## E2E clipboard-with-cli.sh: LARGE-step flake
Reproduced. Counts for the LARGE step:

### Root cause (not a script ordering race, not newest-wins)
Single status slot, last writer wins, written by two lanes:
1. L2 copies "other-$$" (`printf | wl-copy` on L2). L2 publishes it. The publish completes ~6.9 s later. Confirmed in 3 failing runs: CLI devA sees the text at T, the big clip at T+6.9 s (run 2: 195.612 -> 202.528; run 3: 25.343 -> 32.205 UTC).
2. The script waits only until L1 has the text (L1 writes it), then `sleep 1`, then history-copy on L2, then offers the 22 MiB clip from L1. Nothing waits for L2's own publish to finish.
3. L1 publishes the big clip (L1 status "Sent to 2 devices." is the big clip's own outcome). L2 receives it: `run_files` -> `on_large` -> notification "Large file clip" -> status "Large file clip (21 MiB)..." (platform/src/sync/shared_files.rs:24).
4. About 100 ms later, L2's stale "other-$$" publish completes -> `publish()` writes "Sent to 2 devices." over the large-clip status (platform/src/sync/shared.rs:89-91, status.rs:57).
5. The LARGE step polls `clip.last_event` every 0.2 s. The "Large file clip" state lasts ~100 ms, so the poll misses it, and it never reappears -> 30 s timeout -> FAIL.

Trace evidence (diag run 3, local time UTC+7): 11:27:54.156 L1 status = "Sent to 2 devices." (big publish done); 54.200 L2 notification "Large file clip" (app-L2.log 04:27:54.200Z); 54.295 L2 status = "Sent to 2 devices.". Sample at 54.156 showed "Received files from devL1."; next sample 54.295. No "Large" sample. Pass/fail split (~3 of 7) matches the poll window odds.

Ruled out: echo guard (outbound.rs:109; the big clip was published, L1 status says so), newest-wins drop (lanes.rs is per lane; inbound and outbound are separate lanes, so no cancel), L2 clipboard replaced (`uri_paths b | grep big.bin` never matched; L2 publishes nothing else), the big clip not delivered (L2 notification proves receipt and on_large ran).

Not verified: why the L2 text publish takes ~7 s. Hypothesis: L1 acks it only after its concurrent 22 MiB publish (debug-built core). Receiver ack is sent after `on_offer` incl. `record_received` (core/fsync-core/src/clip/receive.rs:86-116). Needs a core-side trace to confirm.

### Fix applied (test only)
- `apps/linux/tests/e2e/clipboard-with-cli.sh` lines 317-322: after the "other-$$" wait and `sleep 1`, wait until L2 `clip.last_event == "Sent to 2 devices."` (150 x 0.2 s), then assert. Ensures L2's own publish settled before the LARGE offer. No L2 publish happens in the LARGE step after that.
- Product status clobber stays (see Critical Issues). The fix does not hide it.

## Product issue (not changed; proposed fix)
- platform/src/sync/shared.rs:83-95 `publish()`: writes `status.event(describe(p))` unconditionally when `service.publish` returns. A late outbound outcome overwrites a newer inbound event.
- platform/src/sync/status.rs:57: `event()` is a single `last_event` slot shared by both lanes.
- Impact: UX only. The user gets the "Large file clip" notification but the status line says "Sent to 2 devices." (stale). No data loss: clip delivered, held, history row present, not downloaded.
- Proposed fix: capture a status sequence before `service.publish` and write the outcome only if no other event was written meanwhile (`StatusCell` conditional event). Or give send outcomes their own field (`last_send`) apart from receive events. Either removes the clobber. Add a unit test in platform/src/sync/tests_*.rs with a slow fake publish and a concurrent inbound event.
