# fsync backend API (v1)

JSON over HTTPS; authenticated routes take `Authorization: Bearer <access>`. Types live in `fsync_proto::api_dto` / `fsync_proto::presence`. Errors: non-2xx with `{"code","message"}` (`ApiErrorBody`); codes: `bad_request` 400, `unauthorized` 401, `not_found` 404, `conflict` 409, `refresh_in_progress` 409, `reauth_required` 401, `unavailable` 503, `invalid_chain` / `trust_reset_required` 422, `rate_limited` 429 (+`Retry-After`), `internal` 500. Requests over 15 s get 408; the global in-flight cap (`MAX_IN_FLIGHT`) returns 503 `unavailable` (+ fail-closed DB errors). Timestamps are unix ms. Body limit 64 KiB. Auth bad-input responses are deliberately uniform (no account/code oracle).

## Auth
| Route | Body -> Response |
|---|---|
| `POST /v1/auth/otp/start` | `{email}` -> 204. Always 204 for a well-formed email (no enumeration). 400 malformed, 429 over limit. |
| `POST /v1/auth/otp/verify` | `{email, code}` -> `{access, refresh, account_id}`. 401 for wrong/expired/used/locked code. Creates the account on first success. |
| `POST /v1/auth/refresh` | `{refresh}` -> `{access, refresh}`. Rotates; 401 if unknown/expired/revoked; 409 `refresh_in_progress` if the token was rotated < 10 s ago (retry with the newer token; family untouched). |
| `POST /v1/auth/logout` | `{refresh}` -> 204. Revokes the whole session family, including already rotated tokens. The core client treats 401 as already revoked and retries on network failure (see ffi-contract `logout()`). |
| `DELETE /v1/account` | Needs fresh auth (below). -> 204. Erases account, tokens, device lists + history, pairing codes. Open presence sockets are dropped. |

- OTP: 6 digits, keyed-hash stored, TTL 10 min, 5 attempts (every guess counts), single use. Email is trimmed + lowercased. `start` while a live code younger than 60 s is pending is a no-op (still 204; the existing code stays valid, so a third party cannot lock the owner out by hammering it). A new code replaces the old one if none exists, it expired, is burned, or the live code is older than 60 s (resend after a lost email). If the email provider fails, the just-created code is deleted and the call returns 500, so the client can retry at once. Only starts that create a code count toward the per-email limit; no-ops count only toward the per-IP limit. Verify does a constant-time dummy compare when no code exists.
- Access token: EdDSA JWT (`{sub, sid, auth_time, iat, exp}`), 15 min. Every authenticated request and the presence handshake also require the `sid` family to be live (an unrevoked, unexpired refresh token exists), so logout, family revocation and account deletion invalidate outstanding access tokens immediately. `sid` = refresh family id; `auth_time` = unix s of the OTP verify, carried unchanged through refresh. Refresh: opaque, 30 d, stored hashed.
- Refresh families live at most 90 d from the OTP login (no extension by rotating); an account keeps at most 20 live families (oldest revoked). **Reuse of a refresh token rotated > 10 s ago, or revoked, revokes its entire family** and closes its presence sockets.
- Lost refresh response (known limitation): tokens are stored hashed only, so the server cannot replay a response. If a client rotates but never receives the new pair and retries with the old token < 10 s later it gets 409 `refresh_in_progress` (retry later with the newer token, which it does not have); after 10 s the retry is treated as reuse and the family is revoked. The client must then re-run the OTP login. Clients should persist the new refresh token before using it and treat a lost response as a re-login.
- Fresh auth (step-up): trust reset and `DELETE /v1/account` require `auth_time` within 5 min, else 401 `reauth_required` (client re-runs the OTP flow; core maps it to `FsyncError::ReauthRequired`, see ADR 012).
- Limits: `otp/start` 5/h per email and 20/h per client IP; `otp/verify` 30/h per client IP (plus the per-code 5 attempts). Client IP = socket peer, or, if `TRUST_PROXY_HOPS=N` > 0 **and the socket peer is inside `TRUSTED_PROXIES`** (comma-separated CIDRs; required when N > 0), the entry N positions from the **right** of `X-Forwarded-For` (the entry appended by your outermost trusted proxy when N = number of proxies; client-prepended entries are ignored). `X-Forwarded-For` from any other peer is ignored. Missing/malformed header, a non-UTF-8 header line (the whole header is distrusted, no index shift) or fewer than N entries: fall back to the peer address. IPv6 is bucketed by /64. Rate-limit maps are capped (100k keys; expired keys pruned, otherwise arbitrary eviction).

## Device list
| Route | Notes |
|---|---|
| `GET /v1/device-list` | -> `{signed, seq}` (`signed` = base64 postcard `SignedDeviceList`). 404 if none. |
| `PUT /v1/device-list` | Body `{signed}`. `If-Match: <stored seq>`, or absent / `none` when no list exists. 200 + `{signed, seq}`; 409 `If-Match` mismatch or concurrent write; 422 `invalid_chain` (bad signature, signer not trusted, gap, rollback, wrong account, bad genesis, prev-hash mismatch); 400 undecodable. Identical re-PUT of the stored list is an idempotent 200 (checked before `If-Match`). 422 also for shape violations (> 32 devices, device name empty / > 64 chars / control or bidi characters; `fsync_proto::DeviceList::check_shape`). 30 PUTs/h per account (429). |
| `PUT /v1/device-list` + `X-Fsync-Trust-Reset: 1` | Trust reset (ADR 012). Body must be a valid seq-0 genesis for this account; replaces the chain (stored under `epoch+1`; all older-epoch history rows are deleted; history is pruned to the last 100 rows per account for the current epoch). The 3/day budget is consumed only by resets that succeed (rejected, stale-auth or idempotent re-PUTs do not count). `If-Match` is ignored. Needs fresh auth (401 `reauth_required`), 3/day per account (429), and on success `DeviceListChanged` goes to the account's online sockets (removed devices are closed). Without the header a new seq-0 list gets 422 `trust_reset_required`. |
| `GET /v1/device-list/chain?from_seq=N` | -> `{chain: [b64 signed, ...], earliest_seq, truncated}` ascending, current epoch only, `seq >= N` (default 0), max 100 per call. `earliest_seq` = lowest seq still retained (if the client's pinned seq + 1 < `earliest_seq` the gap cannot be closed contiguously: re-pin via trust UI); `truncated: true` = more lists exist, call again with `from_seq = last + 1`. Both fields are `#[serde(default)]` on `ChainResponse`. Feed to `verify_chain` on top of the pinned list to close a gap. |

The server verifies with `fsync_proto::verify_next` / `verify_genesis` as defense in depth; clients remain the trust root. A successful PUT pushes `DeviceListChanged{seq}` to every connected socket of the account.

Client sync (`sync_device_list`): fetch the chain from the pinned seq; if that page is empty (the account was reset to a shorter chain) or does not connect, `GET /v1/device-list` first, and only when its head is not one the user already declined, fetch the full chain (`from_seq=0`).

## Pairing codes
| Route | Notes |
|---|---|
| `POST /v1/pairing` | `{node_id, relay_url?}` -> `{code, expires_at}` (6 digits, 5 min, unix ms). `relay_url` must be https (http only in dev mode), <= 512 chars. 30/h per account. |
| `GET /v1/pairing/{code}` | -> `{node_id, relay_url}`. Single use; same account only. Unknown/used/expired/other account: 404. 400 if not 6 digits. Every lookup counts toward 30/h per account (bounds guessing; there is no separate per-code counter because a hit consumes the code). |

**Security note (code mode):** the backend generates and sees the 6-digit code, so code-mode pairing is not MITM-proof against a malicious backend. It relies on the mandatory SAS confirmation on both devices; QR mode (secret never leaves the devices) is preferred. Codes are stored as keyed hashes bound to the account id. A node with a live (unexpired, used or not) offer may connect to presence before it appears in the device list.

## Presence (WebSocket `GET /v1/presence`, JSON text frames)
1. Server -> `{"type":"challenge","nonce":<b64 32B>}`.
2. Client (within 10 s) -> `{"type":"auth","access","node_id","sig"}` where `sig` = ed25519 over `"fsync-presence-v1" || nonce` by the device key (`fsync_proto::presence::sign_challenge`).
3. Success: server -> `{"type":"peers","peers":[PeerInfo]}` (first `peers` = ack). Failure (bad token, bad sig, node neither listed nor holding a live pairing offer): socket closed with code 4401, no message.
4. Client -> `{"type":"hello","addrs":{relay_url,direct[]}}` (<= 16 direct addrs, https relay url <= 512 (http in dev mode); loopback/unspecified/multicast/port-0 direct addrs are dropped; > 10 Hello/min closes with 4429) and `{"type":"heartbeat"}` every 20 s. No client message for 60 s closes the socket. Any other/malformed message closes with 4400.
5. Server -> `peer_update` (fields of `PeerInfo` flattened) on peer connect / hello / disconnect (`online:false`, `last_seen_ms`), and `device_list_changed{seq}` after each PUT. Before sending `peers` the server re-checks the device is still listed; a DB error closes the socket (1011, fail closed).

`peers` = every listed device (online or not) plus other online nodes. A *pending* (pairing, unlisted) node gets an empty `peers` and no updates, but listed devices see it. A second connection for the same node replaces the first.

Lifetime and limits: frames/messages > 8 KiB are rejected. The socket closes with 4401 at access-token expiry (reconnect with a fresh token), on logout / family revoke of its session, on account delete, and when its device is removed from the list (closed directly, it gets no `device_list_changed` or peer updates). Heartbeats are limited to 6/min per socket (close 4429; clients send 3/min). A pending (unlisted, pairing) socket is re-checked every 30 s (`pending_recheck`) and closed with 4401 once its pairing offer has expired and the node is still not listed. A device removed from the list never appears online to peers: membership is checked before the socket registers with the hub (and again after). Unauthenticated sockets are capped globally (`MAX_UNAUTH_WS`, 1000) and per client IP (`MAX_UNAUTH_WS_PER_IP`, 10).

## Config (env)
`DATABASE_URL`, `JWT_SIGNING_KEY` (base64, 32 bytes; required unless `FSYNC_DEV_MODE=1`), `BIND_ADDR` (default `0.0.0.0:8080`), `FSYNC_DEV_MODE` (refused when `FSYNC_ENV=production`), `FSYNC_ENV`, `TRUST_PROXY_HOPS` (default 0 = socket peer address; N = proxies in front, see Limits), `TRUSTED_PROXIES` (comma-separated CIDRs of those proxies; startup fails if hops > 0 and it is empty), `PRESENCE_TIMEOUT_SECS` (60), `MAX_UNAUTH_WS` (1000), `MAX_UNAUTH_WS_PER_IP` (10), `MAX_IN_FLIGHT` (512). OTP email: `EMAIL_SENDER=log|smtp` (default `log`, which only logs; with `FSYNC_ENV=production` startup fails unless `EMAIL_SENDER=smtp` or `ALLOW_LOG_EMAIL=1`, the explicit private-staging opt-out), and for `smtp`: `SMTP_HOST` (default `smtp.gmail.com`), `SMTP_PORT` (default 587 = STARTTLS, always required, no plaintext fallback; 465 = implicit TLS), `SMTP_USERNAME`, `SMTP_PASSWORD` (Gmail App Password; spaces are ignored), `SMTP_FROM` (`fsync <addr@example.com>`). Config is validated at startup and the password is never logged; an SMTP failure on `POST /v1/auth/otp/start` returns the generic `500 internal` (details only in the server log, never the code or address) and the unsent code is discarded. Transport timeout 10 s per operation, 12 s per send (a timeout is ambiguous: the code and all send counts are kept, other failures refund them). Consumer Gmail allows about 500 recipients per day. `GET /health` -> `ok` (checks DB); it is exempt from the in-flight cap. The server reads request headers with a 10 s timeout (hyper `header_read_timeout`, HTTP/1; slowloris guard) via `fsync_backend::serve`; there is no global connection cap, so keep the port firewalled to your reverse proxy / load balancer, which should enforce its own connection limits. See `deploy/backend/.env.example`.

## Changelog notes
- Migration `0002_refresh_session` (auth_time / rotated_at on refresh tokens) invalidates sessions that existed before it: old refresh rows get `auth_time = 0`, so they fail the 90-day family check and users must log in again. Acceptable pre-launch; plan a backfill if it ever has to run against live data.
- Round 2: OTP resend + send-failure cleanup, `TRUSTED_PROXIES`, access tokens bound to a live session family, older-epoch history pruning, `earliest_seq` / `truncated` on the chain endpoint, header-read timeout, heartbeat rate limit, success-only reset budget.
