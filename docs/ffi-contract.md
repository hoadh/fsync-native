# FFI contract v2 (fsync-ffi, UniFFI 0.29.4)

Source of truth: `core/fsync-ffi/src/*.rs` (proc-macros). Swift is generated by
`scripts/gen-bindings.sh`; the macOS package is `apps/macos/Packages/FsyncCoreKit`. C# is
generated by `scripts/gen-bindings-cs.ps1` (uniffi-bindgen-cs v0.10.0+v0.29.4) into
`apps/windows/src/Fsync.CoreBindings` (namespace `Fsync.Core`, free functions on `FsyncFfi`,
errors as `FsyncException.<Case>`); C# specifics in ADR 008.
`contract_version()` returns `2`. Changes are additive; breaking changes bump the version (v2: trust-reset API, `FsyncError::ReauthRequired`, `AccountEvent::TrustReset`). Additive changes since v2 do not bump it (see "Additive since v2"): `EngineConfig.relay_urls`, `FsyncEngine.logout_confirmed()`, free function `revoke_session`.

## Threading rules
- All `FsyncEngine` methods are synchronous and blocking. Call them off the UI thread, and never
  from a tokio worker.
- Delegate callbacks run on ONE dedicated background thread ("fsync-callbacks"), in event order.
  A callback may call engine methods. Marshal to the UI thread inside the callback.
- A slow callback delays later callbacks (queue of 4096; overflow drops the event with a warning).
- Releasing the last reference to the engine stops it (blocks up to ~5 s). Call `stop()` first.
- Key material (`device_secret`, `history_key`) comes from the app's Keychain / DPAPI. Session
  tokens are persisted by the app (`on_session_changed`), never by core.
- `start()` takes an exclusive lock on `<data_dir>/engine.lock`; a second engine on the same data
  dir fails with `Invalid("another fsync engine is already running on this data directory")`. The
  lock is released by `stop()` or when the engine is dropped.
- `logout()` takes the refresh token first, then clears tokens, presence and pinned trust. Network
  errors are not surfaced (local ones are). Revocation (whole session family) is tried once inline
  (bounded to 3 s), then retried in the background (5 s doubling to 5 min) while the engine lives.
  The refresh token is never persisted by core: if the app quits first, it stays valid until its
  30-day expiry. Hosts close that gap with `logout_confirmed()` + `revoke_session` (see "Hard
  logout after quit").
- `on_session_changed` delivers each rotated token pair outside core's token lock. Do not call
  `logout()` from it and block on the result. After `logout()` returns, no session callback from a
  refresh that began earlier is delivered.

## Semantics worth knowing
- The denylist is stored only; the app enforces it before `publish_clip`.
- `pairing_offer` supports one secret at a time, hence the `mode` argument. The offer lives 5
  minutes. The offering (new) device receives `ConfirmRequest` as a pairing event; the joining
  (existing) device gets the SAS as the return value of `pairing_join`. Both then call
  `pairing_confirm(request_id, accept)`; `Completed` follows on both. The window is opened
  inside `pairing_offer`, so a second offer while one is open throws `Invalid`; call
  `pairing_cancel` first. `pairing_cancel` also ends a join in progress. A newer confirm
  request invalidates the older `request_id` (the older one counts as rejected).
- Service calls block: call them from a thread outside any tokio runtime. From async code they
  return `Internal` instead of panicking. Dropping the engine inside a runtime is safe.
- `send_files` fails with `PeerOffline` if the peer did not take the offer. A `Send` transfer is
  `Done` when the receiver finished downloading (it is a push; cancelling only stops tracking).
- `fetch_file_to` never overwrites; the final path is in the `Receive` `Done` event.
- `AccountEvent::HistoryReset`: the history database is genuinely corrupt (fails integrity / not
  SQLite); the old file was moved aside (`backup`) and a new history started. Backups are pruned
  to the newest 3, and a backup that holds data is never deleted in favour of an empty one.
- `FsyncError::HistoryKeyMismatch` (from `FsyncService::new`): the supplied history key is not the
  one the database was created with (tracked by a keyed tag in `history.keycheck`). Nothing is
  moved or replaced; the app may retry with the right key, or, after the user confirms, call
  `reset_history(data_dir)`. A legacy database without a tag and a wrong key is treated as
  corrupt (moved aside, `HistoryReset`).
- `reset_history(data_dir) throws` (free function; `FsyncService::reset_history` in Rust,
  `fsync-cli history reset --yes`): moves `history.db*` aside as `history.corrupt-<ts>*` (nothing
  is deleted) and clears `history.keycheck`, so the next `FsyncEngine(...)` with the current key
  succeeds with an empty history. It also drops pinned trust stored in the history database:
  the device must re-pair (or go through trust reset). Call it only while no engine uses
  `data_dir`; a missing directory is not an error. Old backups are pruned only after a
  move-aside, and a backup larger than an empty database is never deleted.
- `Published.delivered` means the transport acknowledged the whole frame (QUIC stream stopped
  cleanly); it does not mean the peer accepted or applied it. A peer refusal is an error
  (`Invalid`) and is not retried; a timed-out or failed attempt is retried once on a fresh
  connection. Each attempt has one deadline covering connect and send (first attempt 2 s, retry
  `send_timeout`, 5 s default), so `publish` returns within about 7 s even if a peer is dead.

- Trust reset. `AccountEvent::TrustReset` fires once per offered list, with the device names it
  would trust; it fires again with a new `reset_id` if the offer grows before the user answers. Show the warning, then call `confirm_trust_reset` or
  `decline_trust_reset`; an app that missed the event asks `pending_trust_resets()` (the list is
  filled by `ensure_account` and presence syncs, and is empty after a restart until the next
  sync). Unknown, answered, superseded (offer grew) or malformed ids throw `NotFound`, also when a
  confirm and a decline race. Confirming when this device is not in
  the new list emits `SelfRemoved`, stops presence and serving, drops the old pin and returns
  `NeedsPairing`: pair it with the new device (`pairing_offer` here, `pairing_join` there).
  Declining keeps the old pin and the root is not offered again in this run (not persisted).
- App guidance: the `TrustResetPrompt` SwiftPM library (apps/macos/Packages/FsyncCoreKit) implements this
  prompt. Create `TrustResetPromptModel(engine:)`, call `refresh()` at launch (answers take the `resetId` that was on screen), and forward
  `AccountEvent` to `handle(_:)` after hopping to the main actor (delegate callbacks arrive on a Rust thread).
- `reset_account_trust` is for a user with no device to pair with. It replaces the account's
  device list with one that holds only this device, so every other device gets a `TrustReset`
  (at most 3 resets a day per account). `FsyncError::ReauthRequired`: the login is older than 5
  minutes; run `login_start` / `login_verify` and call it again. Other errors: `Auth` (no
  session), `Invalid` (the account has no device list yet, or this device is pinned to another account), `Network`
  (rate limit, backend down).
- Old devices are disconnected by the reset and cannot reconnect, so they learn of it on their
  next `ensure_account` (launch / foreground), not by push.
- `AccountEvent::TrustReset` gained fields and `FsyncError` a case, so Swift `switch` statements
  over them must be updated: that is why `contract_version()` is now 2.

## Additive since v2 (no version bump)
- Multiple relays. `EngineConfig.relay_urls` (uniffi default `[]`, so existing hosts compile
  unchanged) is merged with `relay_url`: `relay_url` first, then `relay_urls`, duplicates dropped
  (`https://a` and `https://a/` are one relay). All of them go into one iroh `RelayMap`; the
  endpoint probes them and picks its home relay by latency (and moves it when the network
  changes), so a US-East-2 and a Singapore relay need no host logic. A peer that cannot reach one
  relay uses the other. The relay a device reports in presence is its current home relay.
  Validation happens in `FsyncEngine(...)`: an unparsable URL or any scheme but `https` throws
  `Invalid` (plain `http` only with `allow_insecure_http`); one bad entry fails the whole list.
  `force_relay` still means relay-only, and needs at least one relay.
- `logout_confirmed() -> Bool`: exactly `logout()` (same local sign-out, same 3 s inline bound),
  plus the one thing `logout()` cannot say. `true`: the backend settled the revocation (revoked,
  already dead = 401, or refused for good, which a retry cannot change). `false`: the revocation
  is only queued in memory (backend unreachable) or the engine held no session. A new method, not
  a changed return type of `logout()`, so Swift/C# callers of `logout()` compile as before.
- `revoke_session(api_url, refresh_token, allow_insecure_http) throws`: revokes the whole session
  of `refresh_token` through the same backend client and revoke call as `logout`, without an
  engine. Blocking, bounded to about 10 s (connect, TLS, request, response); call it off the UI
  thread. `Ok`: revoked, or already revoked (401, also for an unknown token): delete your copy.
  `Network`: no answer in time, 5xx or 429: keep the token and retry later. `Invalid`: bad URL,
  plain http without `allow_insecure_http`, empty token, or a refusal a retry will not change:
  final. Refuses to run inside an async runtime (`Internal`).

## Hard logout after quit (host pattern)
Core never persists the refresh token, so a revoke that could not finish before the app quit
would leave the token valid for up to 30 days. Hosts do this (macOS: `PendingRevoke` and
`PendingRevokeResume` with `AppSecrets` in FsyncMacCore, on the Keychain):
1. On logout, BEFORE calling `logout_confirmed()`, store the current refresh token in the secure
   store as a "pending revoke" with the API URL and the time (use the newest token the host
   got from `on_session_changed`).
2. Call `logout_confirmed()`. On `true` delete the pending revoke. On `false` or an error keep it.
3. At every launch, if a pending revoke exists, call `revoke_session` off the main thread. Delete
   it on `Ok` (this includes 401) and on a final error (`Invalid`). On `Network` keep it and
   count the failure.
4. Drop it, whatever the outcome, after 5 failed launches or 30 days (the token has expired by
   then). Never block startup on it, and never log the token.
A second `revoke_session` for the same token is harmless (401 counts as success), so a crash
between a successful revoke and the delete only costs one extra call.

## v0 -> v1 differences
| v0 (phase 03) | v1 |
|---|---|
| `pairing_offer()` | `pairing_offer(mode)` (code or QR) |
| `pairing_join` returned immediately | returns `PairingPeer` once the SAS is ready |
| `publish_clip -> ItemId` | `-> Published` (echo / delivered / failed) |
| config without secrets | `device_secret`, `force_relay`, `allow_insecure_http` added |
| no sign-in calls | `login_start`, `login_verify`, `set_session`, `logout`, `ensure_account` |
| 6 callbacks | + `on_account_event`, `on_session_changed` |
| `fetch_file_to(.., dest_path)` | `dest_dir` (directory, never overwrites) |
| `FilesOffer` type | `ClipItem` with `push = true` |
| errors without `Invalid`/`Internal` | both added |
| `Device.status` only | + `online` (backend presence) and `is_self` |
| - | `node_id()`, `contract_version()` |
