# ADR 012 — Account recovery = trust reset + re-pair
Status: accepted — validation S1. Implemented 2026-10-14 (review item M5): `reset_account_trust`, `confirm_trust_reset`, `decline_trust_reset`, `pending_trust_resets`. `logout` still clears pinned trust; this API is what makes that recoverable.

If all devices are lost, the user logs in and creates a new seq-0 DeviceList (re-genesis). Old devices still holding the previous chain see the same account with a different root and show a "Trust reset" warning that requires explicit confirmation. No recovery key in MVP; history is local so nothing server-side is lost.

## Flows (M5)

**Initiate (no device left to pair with).** The user signs in with a fresh OTP and calls `FsyncService::reset_account_trust()` (CLI: `fsync-cli account reset-trust --yes`). It needs a session and an existing server-side list, but no local pin. The device signs a new seq-0 genesis that contains only itself and sends it with `X-Fsync-Trust-Reset: 1`. Before the server is asked, a local pin of another account is refused (`Invalid`, WrongAccount). While the reset runs the device ignores resets of its own (an in-flight counter in the trust manager, so overlapping resets do not clear each other), so the push that follows is not announced to itself. On success it replaces its local pin (dropping any old pin and pending / declined resets), restarts presence and returns `Created`. If the server accepted but pinning failed locally the error says so (`Internal`); calling again finishes it without a new reset: when the server's list is already a seq-0 root that lists only this device, that list is pinned and nothing is sent. The backend wants a login from the last 5 minutes: a 401 `reauth_required` becomes `FsyncError::ReauthRequired`, nothing changes locally, and the app re-runs the OTP and retries. The backend allows 3 resets a day per account.

**Respond (every other device).** A device that syncs and finds a seq-0 list with a different root of the same account holds it as pending and emits `AccountEvent::TrustReset { reset_id, devices, device_names }`. `device_names` are the names in the offered list, so the user sees who would be trusted (they are chosen by whoever made the reset: show them as untrusted text). `reset_id` is the lowercase hex of the hash of the offered *head*, the same on every device that sees the same list. `pending_trust_resets()` lists what is waiting. Nothing is trusted until the user answers.

**Consent is bound to what was shown.** The id names the offered head, not just the root. If the server extends the offered chain before the user answers, the pending entry takes the new head, the event fires again with the new id and names, and the old id is dead: confirming or declining it gives `NotFound`, so an answer can never pin a list the user did not see. (Alternative considered: id = root, confirm pins the latest head; rejected because the prompt could be stale.)

- Answers:
  - `confirm_trust_reset(reset_id)` pins the head the id names. If this device is not in the new list, `SelfRemoved` fires, presence stops, the connections close, and the old pin is dropped (pairing refuses to run over an existing pin). The result is `NeedsPairing`; the user pairs it with the new device. If it is listed the result is `Ready`.
  - `decline_trust_reset(reset_id)` keeps the old pin. The root is remembered as declined (up to 32, only the user's answers add to it), so later syncs neither announce nor list it again, even when its chain grows, and the sync skips the full-chain fetch while the server's head is the declined one.
  - Unknown, answered, superseded or malformed ids are `NotFound`, also when a confirm and a decline race (one wins, the other is `NotFound`).

Consequences. A reset closes the sockets of every removed device, and those cannot reconnect, so an old device learns of the reset on its next `ensure_account` (app launch or foreground), not by push. Pending and declined state is in memory only (a decline from a separate CLI process does not persist): after a restart the next sync announces the root again. Only one offered root is pending: a different new root replaces it (an honest server serves one chain), so stale ids give `NotFound` and a new root is never dropped. Confirming clears all pending entries. While this device runs its own reset, foreign roots are ignored (not queued); the next sync offers them again. A device that declines keeps trusting the old list, which the server no longer serves; it can only talk to peers that still hold the old pin until the user signs out or confirms.
